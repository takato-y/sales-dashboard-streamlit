## 背景

当初は集計を pandas で書いていた。指標の定義を業務システム側（社内のデータベースや BI ツール）でも使えるようにしたい、計算式を出力物ごとにずらしたくない、という理由から、集計を SQL に移すことにした。

## 検討した案

| 案 | 長所 | 短所 |
|---|---|---|
| A. pandas のまま | 追加の仕組みが不要 | 計算式が Python の中にあり、他のツールから使えない |
| B. SQLite のビュー | Python に含まれ、追加の導入が不要。メモリ上に置けばディスクに残らない | 型が緩い（金額は REAL）。複数人の同時利用には向かない |
| C. DuckDB のビュー | 集計が速く、列指向 | 追加の導入が必要。この規模では B との差が小さい |
| D. SQL Server | 業務システムと同じ | 利用者の PC に導入できない。ローカル専用の要件に合わない |

## 決定

B を採用する。計算式は標準的な SQL（CTE・ウィンドウ関数）で書き、SQL Server へ移す場合の T-SQL 版を `sql/sqlserver/` に置く（未実行）。Python に残すのは読み込み・検証と、条件の書き込み・ビューの読み出しだけとする。

## 結果

- 集計の自動テストは、ビューの結果を標準ライブラリだけの計算と突き合わせる形にした（TC-020〜TC-034）
- pandas で書いていた集計（`kpi.py`・`analysis.py`）は削除した。同じ計算を 2 か所に持つと、片方だけ直す誤りが起きるため
- ABC の区切りの値（70%・90%）はビュー `v_abc_customer`・`v_abc_product` に置いた（ADR-0002 を更新）
